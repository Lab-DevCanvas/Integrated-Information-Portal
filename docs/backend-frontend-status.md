# 요구사항 대비 백엔드·프론트 구현 상태

확인일: 2026-09-10. 기준은 첨부된 Opportunity Collector 요구사항정의서의 요구사항/개발 로드맵/데이터 계약과 `../crawling`의 실제 라우터·스키마·서비스·저장소·수집기 코드다. 문서에 적힌 향후 계획과 실행 지시는 구현 완료 근거로 취급하지 않았다. 기존 프론트의 미커밋 변경은 보존했으며, 이 작업에서 crawling 저장소와 운영 데이터는 변경하지 않았다.

## 백엔드 단계 확인

| 단계 | 코드에서 확인된 구현 | 남아 있는 범위 |
|---|---|---|
| 0 기반 계약 | SourceConfig CRUD 중 등록·수정·조회, 정책 상태, 활성화 제어; raw/common DTO; 안정적인 opportunity_id 보완 | 요구문서의 최종 Opportunity 계약 전체와는 차이 있음; RBAC 없음 |
| 1 수집 | 11개 소스 레지스트리, API/웹 수집기, raw/common upsert, 날짜 정규화, cron 진입점, 수동 수집 작업과 단건 상태 조회 | 첨부 수집·SSRF 통제·내구성 있는 큐 등 전체 완료 조건 충족을 의미하지 않음 |
| 2 정제 | 기존 소스별 필드 매핑과 기간 파싱 | AI 추출, 8종 분류, 자격 rule_json, 교차 출처 병합/분리, 버전 diff, 품질 게이트는 실행 전 계획 단계 |
| 3 저장·검색 | MongoDB 공고 목록/상세, 출처·카테고리·기간 상태 필터, 페이지네이션 | 키워드 검색·정렬·검색 인덱스·구조화 자격 필터 없음 |
| 4 운영 | 소스 제어, 수집 POST/단건 GET, raw 조회 | 전체 작업 이력 목록, 검수 큐, 재처리/dry-run, KPI API 없음 |
| 5~7 자격·추천·Agent | 해당 서버 API 없음 | 기존 프론트의 로컬 프로필·점수·검색 파서는 서버 구현과 구별해야 함 |

근거: `src/api/routers/{activities,source_configs,crawl_jobs,raw}.py`, `src/api/schemas/`, `src/common/crawl_runner.py`, `src/common/source_registry.py`, `src/common/dto/`, `logs/opportunity-collector.md`.

SourceConfig의 schedule/rate_limit은 저장되지만 그 값으로 실행기를 재설정하는 기능까지 구현된 것은 아니다. 코드 레지스트리에 없는 새 소스를 등록해도 수집기가 생기지 않는다. SourceConfig가 없는 기존 소스는 실행 허용으로 처리된다. 수동 작업의 중복 검사는 같은 target 기준이며 전체 실행과 개별 실행의 상호 배제, 원자적 잠금, 자동 복구까지 보장하지 않는다.

## 이번 프론트 변경

후속 요청 반영: 전체 공고 기능을 `/categories`로 통합했다. 프로필 없이 탐색할 수 있으며 검색·상세 필터·정렬·출처·모집 상태를 URL에 유지한다. 첫 20건 이후 점진 로딩과 무한 스크롤로 이어 표시한다. 2026-09-17 요청에 따라 관리자 페이지·운영 API 프록시·운영 키 설정을 제거했다. 소스 관리·수동 수집·raw 조회는 현재 프론트 제공 범위에서 제외한다.

| 요구사항 | 구현 |
|---|---|
| REQ-IF-001, REQ-F-016 지원 범위 | `/categories`: 출처/4종 카테고리/모집 상태 필터, 총 건수, 점진 로딩·20건 단위 무한 스크롤, URL 상태, 로딩/빈 결과/오류/재시도 |
| REQ-DA-001, REQ-F-016 | 기존 상세 UI에 실제 DTO 매핑, 원문 링크, optional opportunity_id 호환 |
| REQ-NF-002 | 전체 조회 실패를 성공한 빈 배열로 숨기지 않음; 부분 실패 안내; 재시도; 상세의 API 장애와 404 구별 |
| REQ-NF-003 일부 | 프록시 경로 제한/오류 전달, 부분 실패, 불명확한 자격/날짜에 대한 자동 테스트와 브라우저 확인 |

브라우저는 동일 출처 `/api/crawling`을 호출하고 Next.js 서버가 설정된 백엔드로 전달한다. HTTPS 프론트에서 HTTP 백엔드를 직접 호출하던 mixed-content 문제를 피한다. 공고 목록·상세 GET만 전달하며 운영 경로와 쓰기 메서드는 제공하지 않는다.

기존 대시보드는 카테고리별 25건 샘플을 계속 사용한다. 전체 탐색은 새 `/categories` 화면에서 한다. 저장/계획/비교 ID가 샘플 밖에 있으면 단건 API로 추가 조회한다. 상세에서 방문한 공고도 메모리 목록에 반영한다. 사용자 프로필·저장·지원계획은 기존대로 이 브라우저의 로컬 데이터다.

누락된 날짜는 빈 값으로 유지하여 ‘마감일 미상’으로 표시하고 가짜 캘린더 일정을 만들지 않는다. 수집 데이터의 자격 판정은 `unknown`이다. 후속 UI 복원 요청에 따라 상세는 기존 OpportunityDetail 레이아웃으로 복원했다. 해당 화면의 점수·분석 영역은 기존 로컬 모델이며 정식 백엔드 분석 결과가 아니다. 기존 로컬 추천 모델의 경쟁률·포트폴리오 중간값 등 호환 필드는 남아 있으며 서버 기반 정식 추천은 후속 작업이다.

## 로컬 코드와 실제 배포본 차이

2026-09-10 기본 배포 주소에 읽기 전용 요청을 보냈다.

- `GET /activities?page_size=1`: HTTP 200, total 1819.
- `/openapi.json`: activities/raw/crawl-jobs/health 경로 존재, **source-configs 경로 없음**.
- 배포된 Activity 응답에는 `opportunity_id`도 아직 없음. 클라이언트는 optional로 수용한다.

이 차이는 당시 배포 상태를 기록한 것이며 현재 프론트는 소스 관리 기능을 제공하지 않는다. 실제 운영 크롤러나 운영 데이터는 변경하지 않았다.

## 실행 및 검증

`.env.example`을 참고하여 `.env.local`에 CRAWLING_API_URL을 설정한다. 기존 NEXT_PUBLIC_CRAWLING_API_URL도 하위 호환하지만 서버 전용 변수를 우선한다.

검증 명령: `npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build -- --webpack`. 기본 Turbopack 빌드는 이 실행 환경의 포트 생성 제한으로 실패했고 Webpack 빌드는 통과했다. 외부 폰트 다운로드가 필요하다.

2026-09-17 최종 검증: 20개 파일의 테스트 204개, ESLint, Webpack 프로덕션 빌드와 빌드 내 TypeScript 검사 통과. 빌드 경로에 `/admin`이 없음을 확인했다. 백엔드 전체 테스트와 서비스 배포는 이 프론트 작업의 검증 범위에 포함하지 않는다.

## 2026-09-17 카테고리 점진 로딩 및 후속 과제

- 첫 요청은 `page=1&page_size=20`으로 전체 건수(`total`)와 첫 20건을 받아 즉시 표시한다. 백엔드 계약은 변경하지 않는다.
- 이후 최대 4개 요청으로 100건 단위 백그라운드 조회를 진행하며 받은 결과를 순차 반영한다. `page_size`에 따라 페이지 오프셋이 달라지므로 백그라운드는 100건 기준 1페이지부터 조회한다. 첫 20건의 중복 전송을 허용하고 ID로 중복 제거하여 21~100번째 데이터 누락을 방지한다.
- 화면은 API 전체 건수, 지금까지 불러온 건수, 현재 로컬 조건에 맞는 건수를 구분한다. 현재 불러온 결과는 무한 스크롤로 20건씩 추가 표시한다. 로딩 중 검색 결과가 없으면 검색 진행 상태로 표시한다.
- 추가 조회가 실패해도 이미 받은 결과는 유지하며 재시도를 제공한다. 취소된 요청의 늦은 응답은 반영하지 않는다. 완전히 받은 결과만 메모리에 1분간 캐시한다.

### 나중에 해결할 문제

사용자 요청에 따라 다음 문제는 이번 단계에서 허용하고 후속 작업으로 남긴다.

- **적합도와 정렬 순서 변동:** 첫 20건의 적합도순은 전체 데이터의 적합도순이 아니다. 백그라운드 데이터가 추가되면 목록 순서와 각 페이지에 속한 공고가 바뀔 수 있다.
- **검색·필터 결과의 지연 등장:** 아직 받지 못한 공고는 로컬 검색에 포함되지 않으므로 일치 건수와 페이지 수가 조회 중 증가할 수 있다.
- **전체 데이터 다운로드:** 첫 화면 표시만 앞당겼으며 전체 전송량은 줄이지 않았다. 백엔드 검색·필터·전역 정렬 지원 후 현재 페이지와 다음 페이지 위주로 요청하는 구조로 전환한다.
- **스크롤에 따른 API 조회:** 현재 스크롤은 화면에 표시하는 카드 수를 늘리고, API는 전체 데이터를 백그라운드에서 받는다. 서버 검색·정렬 지원 후 스크롤 위치에 따른 다음 데이터 요청과 프리패치로 전환한다.
- **페이지 간 데이터 일관성:** 수집 중 `last_seen_at` 정렬이 바뀌면 오프셋 조회에서 누락·중복이 발생할 수 있다. `_id` 보조 정렬과 커서/스냅샷 방식을 검토한다.

### 무한 스크롤 반영

이전·다음 버튼과 페이지 번호 표시를 제거했다. 첫 20건 표시 후 목록 하단 400px 이내에서 다음 20건을 이어 붙인다. 필터·검색·정렬 변경 시 표시 개수를 초기화한다. 백그라운드 데이터 대기, 부분 실패, 전체 결과 표시 완료 상태를 구분한다. 기존 `page` URL 값은 무시하고 필터 변경 시 제거한다.
